# Steward: carry a PR to "ready to merge"

The user merges; nothing else does. Your job is to make every open PR mergeable and keep it that way, without being asked
twice. Follow CLAUDE.md throughout (workflow, attribution, test tiers, "one answer per question").

## When a PR exists

1. **Subscribe** to it at once (`subscribe_pr_activity`). Do this for every PR you or your agents open, and for any PR the user
   asks you to watch. Events (CI results, review comments, reviews, merge) then wake you; never poll or sleep.
2. Keep one **safety-net check-in** (`send_later`, about 50 minutes after the last activity) while a PR only waits on CI or review,
   in case an event is lost. Stop after three empty check-ins in a row, or when the PR merges or closes.
3. Draft PRs get a `@codex review` comment (Codex skips drafts otherwise).

## On every wake: work every open item

Read the PR at its head: check runs, unresolved review threads, mergeability. Then:

- **CI red.** Fetch the failing job's log only, tailed (`gh api repos/<owner>/<repo>/actions/jobs/<id>/logs | grep … | tail`).
  Find the root cause and fix it. "Flake" is not a cause; a job gets one re-run at most. Never skip, weaken, quarantine or loosen
  a test to get green: a test whose claim changed keeps the same claim for the new behaviour. A slow or statistical test that
  fails: report the numbers first. A failure that is red on `main` too is not this PR's: say so once on the PR.
- **Review finding** (Codex or a person). Verify it against the code before acting. Real: fix it in proportion, with a test that
  fails without the fix. Not real or outdated: reply with what you traced. Optional or nit findings never start a push on their
  own; carry them in the next one. Security findings stay open for the user.
- **Reply, then resolve.** Every thread gets a reply saying what was fixed (commit, owner function, test) or why not. Once the
  fix is pushed, **resolve the thread**. GraphQL is unavailable here; use the REST route:
  - list: `gh api repos/<owner>/<repo>/pulls/<n>/ccr/review_threads` (each thread has `resolved` and `comment_ids`)
  - resolve: `gh api -X POST repos/<owner>/<repo>/pulls/<n>/ccr/comments/<first comment id>/resolve`
  A thread with a fix reply must not be left unresolved. Leave a thread open only when it waits on the user's decision.
- **Merge conflict.** Merge `main` into the branch (never rebase, amend or force-push), run the checks, push.
- **Batch.** Gather all fixes for a PR into one push: every push to a ready PR reruns the full CI.

Every reply or comment ends with:

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## Who fixes

- Review and CI fixes go by message to the agent that wrote the PR (CLAUDE.md). Brief it with the finding ids, "verify first",
  "reply and resolve each thread", and "one push". When that agent's context is near 450k, continue with a fresh agent briefed from
  its handoff note.
- Small, confident fixes you may make yourself.
- If a push or commit is refused by permissions, don't work around it: tell the user.

## Ready and merge

- Mark a draft ready (`gh api -X POST repos/<owner>/<repo>/pulls/<n>/ccr/ready_for_review`) once its fixes are in and, for visual
  work, the user approved the screenshots. Ready starts the full CI and another Codex review.
- When CI is green on the head, there are no unresolved threads and no conflict, tell the user the PR is ready to merge, with the
  link. Never approve or merge yourself.
- After the user merges: add the CHANGELOG line under "Unreleased", merge `main` into any PR stacked on it, and unsubscribe from
  the merged PR.

## Report to the user

Short: what came in, what was fixed (and by whom), what is green, what waits on them. Don't relay every event; say when something
changes what they need to do.
